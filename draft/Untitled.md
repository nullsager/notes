## KVFlow 精简总结

**KVFlow** 是一种面向 LLM 多智能体工作流的前缀 KV Cache 管理方案，目标是减少重复 prefill 和 CPU–GPU 缓存传输带来的延迟。

### 核心问题

多 Agent 系统中，每个 Agent 通常有很长且重复使用的固定 Prompt。GPU 显存不足时，传统 **LRU** 可能淘汰“马上要执行”的 Agent 缓存；CPU 分级缓存又通常等请求到达后才加载，导致 GPU 等待。

### 核心方法

1. **工作流感知淘汰**
   - 根据 Agent 工作流图计算每个 Agent 距离执行还有多少步。
   - 优先保留即将执行的 Agent 前缀，淘汰短期内不会使用的缓存。
   - 动态后缀复用率低，因此优先淘汰。
   - 在 Radix Tree 上按节点管理，正确处理多个 Agent 的共享前缀。

2. **提前预取**
   - 在当前 Agent 运行时，预测后续可能执行的 Agent。
   - 异步将其 KV Cache 从 CPU 搬到 GPU，使传输与计算重叠。

3. **状态感知调度**
   - 如果某请求的 KV Cache 仍在加载，就先执行其他缓存已就绪的请求，减少 GPU 空闲。

### 实验结果

基于 SGLang 实现，特定长前缀场景下：

- 相比 HiCache，最高加速约 $2.19\times$；
- 相比原生 SGLang，最高加速约 $2.91\times$；
- 更真实的 PEER 工作流中，提升约 $1.08$–$1.12\times$。

### 结论

KVFlow 的关键贡献是：**利用多 Agent 工作流中可预测的未来执行顺序，而不是仅根据历史访问记录管理 KV Cache。**

它最适合：

- Agent 固定 Prompt 很长；
- Agent 会被反复调用；
- GPU 显存紧张；
- 工作流结构较稳定；
- 多工作流并发且输出较短。

局限是依赖工作流可预测性，分支过多可能产生无效预取，并且主要优化 prefill，对长文本 decode 的帮助有限。



## Agentix 精简总结

**Agentix** 是一个面向 LLM Agent 程序的推理服务系统。它不再把每次 LLM 调用视为独立请求，而是把包含多次调用、工具执行和并行分支的**整个 Agent 程序**作为调度单位。

### 核心问题

传统 vLLM 等系统按单个请求调度，容易产生两类队头阻塞：

- **请求级阻塞**：长生成请求阻塞短请求；
- **程序级阻塞**：调用次数很多的长程序持续阻塞较短程序。

这会显著增加 Agent 程序的端到端延迟。

### 核心方法

1. **程序感知调度**
   - 维护类似操作系统“进程表”的全局状态；
   - 根据程序已经消耗的累计执行时间确定优先级；
   - 优先服务消耗时间较少、可能更快完成的程序，并支持抢占。

2. **适配不同程序结构**
   - **PLAS**：用于单线程 Agent 程序，按整个程序的累计服务时间排序；
   - **ATLAS**：用于并行、动态 DAG 程序，关注各线程及关键路径，避免关键任务被阻塞；
   - 无需预先知道程序完整结构，而是在运行中动态跟踪。

3. **数据局部性感知的负载均衡**
   - 同一程序的调用通常共享大量上下文和 KV Cache；
   - 尽量把长请求路由到已有其缓存的引擎；
   - 对短请求则更重视集群负载均衡。

4. **高效 KV Cache 交换**
   - 批量执行 GPU–CPU KV 块传输，降低抢占导致的缓存交换开销。

### 实验结果

在 Chatbot、ReAct、MCTS 等工作负载上：

- 相比 vLLM，在相同延迟下，程序吞吐量提升约 $4$–$15\times$；
- 相比充分优化的推理引擎，提升约 $2$–$5\times$；
- 多引擎场景下，相比普通负载均衡器最高提升约 $1.5\times$。

### 一句话结论

> **Agentix 将 LLM Serving 从“调度独立请求”提升为“调度完整 Agent 程序”，利用程序级执行历史、并行结构和 KV Cache 局部性，减少阻塞并降低端到端延迟。**

它与 KVFlow 的侧重点不同：**KVFlow 主要优化前缀缓存的淘汰和预取；Agentix 主要优化整个 Agent 程序的请求调度与跨引擎路由。**

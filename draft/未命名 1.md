## 一、开场：项目是什么（2 分钟）

### 你可以这样说：

> "我做的项目是一个**高性能异步日志系统**，叫 AsyncLog，用 C++20 写的。
>
> **日志系统**相当于程序的'黑匣子'，把程序运行中的关键信息记录到文件里，出了问题可以回头查。比如服务器什么时候启动的、某个请求报了什么错，都靠日志。
>
> 像 spdlog、log 4 cpp 这些都是 C++ 常用的日志库，我这个项目就是自己从零实现一个类似的系统。
>
> **为什么叫'异步'？** 因为写日志的线程不需要等文件 I/O 完成，它只需要把消息扔进一个队列就可以继续干活，另外有一个后台线程专门负责从队列里取出消息写入文件。这样主线程几乎不受影响。
>
> 这个项目用到了很多 C++ 高级特性：可变参数模板、折叠表达式、无锁数据结构、编译期优化等等。"

### 老师可能会问的问题 & 回答：

**Q: 为什么选这个项目？**
> A: 日志系统是几乎所有后端服务的基础设施，做这个项目可以同时学到模板元编程、多线程编程、无锁数据结构这些 C++ 核心技术。而且日志系统的需求明确，不需要额外的领域知识。

**Q: 这个和 spdlog 有什么区别？**
> A: spdlog 是一个成熟的工业级库，功能比我这个丰富得多（支持彩色输出、更多后端、更复杂的格式化）。我的项目是学习性质的，重点在于理解原理。不过核心架构是类似的：都用了异步队列 + 后台线程的模式，都用了 source_location 捕获调用位置。

### 你可以这样说：

> "整个系统分为**前端**和**后端**两部分。
>

> 前端和后端之间通过一个**无锁队列**连接。这是整个系统的核心——它让多个线程可以同时安全地写入日志，而不需要任何互斥锁。"

## 三、核心代码讲解（8 分钟）

### 3.1 日志级别（1 分钟）

> 打开 `include/asynclog/LogLevel.h`

> "日志有 5 个级别，从 DEBUG 到 FATAL，数值越大越重要。设置一个最低级别后，低于它的日志就不会输出。
>
> 比较特别的是这里的**编译期过滤**：
>
> ```cpp
> template <LogLevel Level>
> constexpr bool isLevelEnabled() {
>     return static_cast<uint8_t>(Level) >= ASYNCLOG_COMPILE_LEVEL;
> }
> ```
>
> 这个函数在编译时就能算出结果。配合 `if constexpr`，如果某个级别被禁用，相关的代码会被编译器**完全删除**，一条指令都不会生成。这就是所谓的'零开销抽象'。"

### 3.2 格式化引擎（2 分钟）

> 打开 `include/asynclog/Formatter.h`

> "这个文件实现了类似 Python f-string 的功能，用 `{}` 做占位符。
>
> 核心技术有两个：
>
> **第一个是可变参数模板** `template <typename... Args>`，让 format 函数可以接受任意数量、任意类型的参数。
>
> **第二个是折叠表达式**，就是这一行：
>
> ```cpp
> std::vector<std::string> arg_strings = {toString(std::forward<Args>(args))...};
> ```
>
> `...` 会让编译器自动展开参数包。如果传入 3 个参数 a, b, c，编译器会展开为：
>
> ```cpp
> {toString(a), toString(b), toString(c)}
> ```
>
> 然后就是遍历格式字符串找 `{}`，按顺序替换成参数。占位符多于参数就保留，参数多于占位符就追加在末尾。"

### 3.3 无锁队列（3 分钟，重点！）

> 打开 `include/asynclog/LockFreeQueue.h`

> "这是整个项目技术含量最高的部分，实现了 Dmitry Vyukov 的有界 MPMC 无锁队列。
>
> **为什么用无锁？** 传统的 mutex 方案，线程竞争时需要操作系统做上下文切换，开销在微秒级。无锁方案用 CAS（Compare-And-Swap）原子指令，开销在纳秒级，差了三个数量级。
>
> **数据结构**：一个环形数组，每个槽位有一个 sequence 序列号标记状态。两个原子指针 enqueue_pos_ 和 dequeue_pos_ 分别追踪入队和出队的位置。
>
> **入队过程**（指着 tryPush 代码讲）：
> 1. 读取当前入队位置 pos
> 2. 检查目标槽位的 sequence：如果等于 pos，说明空闲
> 3. 用 CAS 尝试把 enqueue_pos_ 从 pos 改为 pos+1
> 4. CAS 成功 → 我抢到了这个位置，写入数据
> 5. CAS 失败 → 其他线程抢先了，重试
>
> **三个关键设计点**（这些老师大概率会问）：
>
> - **`alignas(64)` 防止 false sharing**：enqueue_pos_ 和 dequeue_pos_ 各占一条 cache line（64 字节），这样生产者写 enqueue_pos_ 不会导致消费者的 cache line 失效。
>
> - **容量必须是 2 的幂**：这样可以用位掩码 `pos & mask_` 代替取模 `pos % capacity`，位运算比除法快一个数量级。
>
> - **内存序**：acquire-release 语义保证了数据的可见性。简单说，生产者用 release 写 sequence 表示'我的数据已经准备好了'，消费者用 acquire 读 sequence 表示'我要看到生产者的数据'。"

### 3.4 Logger 主类（2 分钟）

> 打开 `include/asynclog/Logger.h`

> "Logger 是把上面三个组件整合起来的主类。
>
> 有一个巧妙的设计要讲一下，就是 **FormatWithLocation**：
>
> ```cpp
> struct FormatWithLocation {
>     std::string_view fmt;
>     std::source_location loc;
>     // 没有 explicit！
>     FormatWithLocation(const char* fmt,
>         const std::source_location& loc = std::source_location::current())
>     ```
>
> 问题是 `source_location::current()` 必须作为默认参数才能在调用点求值，但可变参数包必须放在最后，两者冲突。解决方案是把格式字符串包在一个结构体里，通过**隐式转换**让 `source_location::current()` 在调用者的上下文中求值。这个技巧 spdlog 和 fmt 库都在用。
>
> 后台线程用的是**批量刷盘**策略：不是每条日志写完就 flush，而是一口气从队列里取出所有可用消息，写完后只 flush 一次，大大减少了系统调用次数。
>
> 析构函数保证了 RAII：对象销毁时自动通知后台线程停止、等待排空、关闭文件，不需要手动调用任何清理方法。"

## 高频问题准备

### 关于无锁队列

**Q: CAS 失败了怎么办？**
> A: CAS 失败说明有其他线程抢先修改了 enqueue_pos_，这时 pos 会被自动更新为最新值，直接进入下一轮循环重试。因为每次重试只是一次原子操作，成本很低。

**Q: 什么是 false sharing？为什么要 alignas (64)？**
> A: CPU 缓存以 64 字节为单位（cache line）操作。如果两个频繁修改的变量在同一条 cache line 里，一个线程修改其中一个变量会导致另一个线程的整条 cache line 失效，即使那个变量根本没变。把它们用 alignas (64) 分开到不同的 cache line 就解决了。

**Q: 内存序是什么？为什么不全用 seq_cst？**
> A: 内存序控制的是"一个线程的写入何时对另一个线程可见"。seq_cst 是最强的保证，相当于全局排序，但开销也最大。这里用 acquire-release 就够了：release 保证"我之前的写入都完成了"，acquire 保证"我能看到对方 release 之前的写入"。relaxed 用于不需要同步的场景（比如读 enqueue_pos_ 读到旧值也没关系，CAS 会纠正）。

**Q: 队列满了怎么办？**
> A: 调用线程会 `yield()`（让出 CPU 时间片）然后重试。这是一种自旋等待策略，适合高吞吐场景。在极端情况下队列满了说明后台线程来不及写入，这时适当的背压（back-pressure）是合理的。

### 关于模板

**Q: 可变参数模板是怎么工作的？**
> A: `template <typename... Args>` 中 `Args` 是一个"参数包"，可以匹配任意数量的类型。`args...` 是值的参数包。用 `...` 可以展开：`toString(args)...` 就是对每个参数调用 toString。编译器在编译时就把参数包展开成具体的代码。

**Q: if constexpr 和普通 if 有什么区别？**
> A: 普通 if 的两个分支都要编译（即使永远不会执行）。`if constexpr` 在编译期就确定走哪个分支，不走的分支**不会被编译**，代码直接消失。这用于基于类型的分支选择，也用于日志级别的零开销过滤。

**Q: 完美转发（std::forward）是什么？**
> A: 在模板函数中，参数经过传递后会"退化"（右值变成左值）。`std::forward` 可以恢复参数原来的左值/右值属性，这样就能避免不必要的拷贝。比如一个临时字符串传进来是右值，用 forward 可以保持右值语义，后面的函数就能用移动而不是拷贝。

### 关于设计

**Q: 为什么用 source_location 而不是 __FILE__ 和 __LINE__？**
> A: `__FILE__` 和 `__LINE__` 是 C 风格的宏，会在宏展开的地方求值。如果用宏包装日志函数，所有日志都会显示同一个文件和行号（宏定义的位置）。`source_location::current()` 可以作为默认参数，在每个调用点分别求值，更优雅也更准确。

**Q: 后台线程为什么要批量写入？**
> A: 每次 flush 是一个系统调用（fsync），涉及内核态切换，开销约微秒级。如果 10 万条日志各 flush 一次就是 10 万次系统调用。批量取出 100 条一起 flush，系统调用减少 100 倍，吞吐量大幅提升。

**Q: 析构函数里为什么要 join？**
> A: join 的作用是等待后台线程结束。如果不 join 就直接销毁对象，后台线程还在访问已经被销毁的成员变量（比如 queue_、log_file_），就会导致未定义行为（通常是崩溃）。join 确保所有队列中的日志都被写入文件后才关闭。

**Q: 这个系统有什么局限性？**
> A: 主要有几点：
> 1. 格式化在主线程完成（spdlog 可以把格式化也延迟到后台线程）
> 2. 队列满时主线程会自旋等待，可能影响延迟
> 3. 只支持文件和控制台输出，不支持网络等其他后端
> 4. 没有实现日志的时间轮转（按时间拆分文件），只有大小轮转

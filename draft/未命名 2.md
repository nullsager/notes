# 第 2 页：项目背景

## 什么是日志系统？

- 日志系统是程序运行时的"黑匣子"，记录程序的运行状态、错误信息和调试数据
- 几乎所有后端服务（Web 服务器、数据库、微服务）都依赖日志系统排查问题

## 为什么需要"异步"？

- 传统同步日志：每次写日志都要等磁盘 I/O 完成，阻塞主线程
- 异步日志：主线程只需将消息放入队列即可返回，后台线程负责写入磁盘
- 性能差距：同步方案在高并发下成为瓶颈，异步方案对主线程几乎零影响

## 项目定位

- 从零实现一个类似 spdlog 的高性能日志库
- 综合运用 C++20 多项高级特性（模板元编程、无锁编程、编译期优化等）

# 第 4 页：系统架构

```
 [线程 A]  \                                          ┌──→ 日志文件
 [线程 B]  ──→  [ 无锁队列 (LockFreeQueue) ]  ──→  [ 后台线程 ] ──┤  (自动轮转)
 [线程 C]  /     CAS 原子操作，零锁开销           批量取出+写入  └──→ 控制台
   生产者                                                消费者
```

**数据流：**
1. 用户调用 `logger.info("用户 {} 登录", id)`
2. 自动捕获调用位置（文件名: 行号）
3. 编译期过滤 --> 运行时过滤 --> 格式化消息
4. 消息入队（CAS 操作，纳秒级）
5. 主线程立即返回，不等待 I/O
6. 后台线程批量取出消息，一次性写入文件并 flush

# 第 6 页：创新点一 -- 无锁队列

## 传统方案 vs 本项目方案

| | 有锁方案（Mutex） | 无锁方案（CAS） |
|--|--|--|
| 线程竞争时 | 阻塞等待，操作系统上下文切换 | CAS 重试，纯用户态 |
| 单次开销 | 1~10 微秒 | 几十纳秒 |
| 性能瓶颈 | 锁竞争导致吞吐量下降 | 近线性扩展 |

## 核心算法：Vyukov's MPMC Queue

- 环形缓冲区 + 序列号状态机
- 入队/出队通过 CAS（Compare-And-Swap）原子指令实现
- 容量为 2 的幂，用位掩码代替取模运算（快 30 倍）

## 三个关键优化

1. **`alignas(64)` 防止 False Sharing**：生产者/消费者指针各占独立 Cache Line，互不干扰
2. **位掩码取模**：`pos & mask_` 替代 `pos % capacity`，1 个 CPU 周期 vs 30 个周期
3. **Acquire-Release 内存序**：精确控制多线程间的数据可见性，避免过强的 seq_cst 开销

# 第 7 页：创新点二 -- 编译期零开销过滤

## 双层过滤机制

```
                    日志调用
                      |
              [编译期过滤 if constexpr]
              ASYNCLOG_COMPILE_LEVEL=2(WARN)
             /                        \
     DEBUG/INFO                    WARN/ERROR/FATAL
     代码完全消失                       |
     零指令，零开销               [运行时过滤]
                                 logger.setLevel(...)
                                /                \
                          低于阈值              通过
                          一次比较(<1ns)       继续格式化+入队
```

| | 编译期过滤 | 运行时过滤 |
|--|--|--|
| 设置方式 | CMake: `-DASYNCLOG_COMPILE_LEVEL=2` | 代码: `logger.setLevel(WARN)` |
| 开销 | 零（代码被编译器删除） | 极低（一次整数比较） |
| 灵活性 | 需重新编译 | 运行中随时可调 |
| 用途 | 发布版去除所有 DEBUG 日志 | 运行中动态调整日志级别 |

# 第 8 页：创新点三 -- C++20 高级特性应用

## 1. 可变参数模板 + 折叠表达式


## 2. `std::source_location` 自动定位

```cpp
// 无需手写 __FILE__ 和 __LINE__，自动捕获调用位置
logger.info("服务启动");
// 输出: [2024-04-05 11:30:45] [INFO ] [main.cpp:15] 服务启动

```

## 3. `if constexpr` 编译期分支消除

```cpp
if constexpr (isLevelEnabled<Level>()) {
    // 级别被禁用时，这整块代码不会被编译，零开销
}
```

# 第 9 页：创新点四 -- 批量刷盘 + 日志轮转

## 批量刷盘策略

- 传统方式：每条日志写完立即 flush --> 10 万条日志 = 10 万次系统调用
- 本项目方式：一次性取出队列所有消息，批量写入后只 flush 一次
- 效果：系统调用次数减少 100 倍以上，吞吐量大幅提升

## 自动文件轮转

- 当日志文件超过阈值（默认 10 MB）时，自动关闭当前文件
- 创建新文件：`log.txt` --> `log.1.txt` --> `log.2.txt` --> ...
- 防止单个日志文件过大，便于管理和归档

## RAII 资源管理

- Logger 析构时自动：通知后台线程停止 --> 等待队列排空 --> 关闭文件
- 无需手动调用 close () 或 stop ()，不会泄漏资源

# 第 10 页：使用示例

## API 调用

```cpp
#include <asynclog/AsyncLog.h>
using namespace asynclog;

int main() {
    Logger logger("app.log");              // 创建日志器

    logger.info("应用程序启动");             // 基本日志
    logger.warn("磁盘使用率 {}%", 85);      // 格式化
    logger.error("连接失败: {}", "db-01");   // 错误级别

    logger.setLevel(LogLevel::WARN);       // 动态调整级别
    logger.debug("这条不会输出");            // 被过滤
}
```

## 输出效果

```
[2024-04-05 11:30:45.123] [INFO ] [main.cpp:5]  应用程序启动
[2024-04-05 11:30:45.124] [WARN ] [main.cpp:6]  磁盘使用率 85%
[2024-04-05 11:30:45.125] [ERROR] [main.cpp:7]  连接失败: db-01
```

每条日志包含：精确到毫秒的时间戳 + 级别标签 + 源码位置 + 格式化消息
